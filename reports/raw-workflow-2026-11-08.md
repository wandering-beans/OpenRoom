# Windows 11でのRAW取り込みと現像の応答時間

異なる公開RAW 23枚を内蔵SSDから取り込んだ。既定のAVIFでは、走査ボタンを押してから完了するまでの平均が38.56秒から14.30秒に短縮した。23枚すべてで現像済みの一覧画像（長辺384px）と閲覧画像（長辺1600px）を保存した。失敗と保留はいずれも0枚だった。

**異なるRAW 1,000枚を900秒以内に処理できるかは未確認。** この23枚での処理時間は1枚あたり0.62秒。1,000枚での目標は1枚あたり0.90秒。NAS環境は利用できなかった。

## 測定条件

- 修正前は `0998eca8557e0a11cc342b19754f8e3cd260d7d6`、修正後は `680b0712bd22631b94d917983ea81f797541e541`。同じPCで、同じRustのReleaseプロファイル、`custom-protocol`、同じネイティブ依存関係を使った。アプリのバージョン表記は両方とも0.7.13。
- Windows 11 Home 10.0.26300、Ryzen 7 8845HS（8コア16スレッド）、メモリ31.29 GiB。GPUはRTX 4060 Laptop（ドライバー32.0.16.2101）とRadeon 780M（32.0.11038.5002）。実RAWのテストログでDirect3DがRTX 4060を使用した。
- 原本の複製、カタログ、生成先はいずれもCドライブの内蔵NVMe SSD（MTFDKBA1T0QFM-1BD1AABGB）に置いた。各試行で空のカタログと新しいWebViewプロファイルを作った。OSのファイルキャッシュは消去していない。使用したRAWのSHA-256を検査し、同じ内容のファイルは1枚と数えた。
- 23枚の合計は543,197,429バイト。Nikon ZRの6枚はNEFの機種タグも確認した。エンジンが報告した原本寸法は6,056×4,032画素（約2,442万画素）。残る17枚も含め、23枚全体では約312万〜4,021万画素だった。[ZRの公開サンプル](https://www.dkamera.de/testbericht/nikon-zr/beispielaufnahmen.html)・[17枚の配布元とハッシュ](raw-heif-samples.json)
- 走査対象フォルダーだけを登録し、実際のデスクトップアプリのグリッドで「再読み込み」を押した。所要時間には走査、両サイズの圧縮・保存、ボタンが再び使えるまでのUI処理を含む。保存結果はカタログとファイルの両方で検査した。修正前は同じビルドを使った追加試験で、修正後は各取り込み試験で、WebViewが46画像をデコードできることと各画像の寸法を確認した。
- 校正用に抽出するカメラ内JPEGを閲覧用には保存しない。今回の23枚でカメラ画像を先行表示した件数は0件。「最初の一覧表示」は現像済みの一覧画像がグリッドに出るまでの時間。

## 取り込み

各ビルドでAVIF、JPEG、JPEG、AVIFの順に実行した。所要時間と一覧表示は各形式2回の平均。メモリと作業領域のピークは、2回のうち大きい観測値を示す。

| ビルド | 形式 | 全23枚（秒） | 最初の一覧（秒） | 生成領域ピーク（MiB） | 残す2サイズ（MiB） | アプリとワーカーのメモリ（GiB） | 再走査（ms） |
|---|---|---|---|---|---|---|---|
| 修正前 | AVIF | 38.56 | 1.62 | 38.50 | 4.22 | 1.97 | 14 |
| 修正前 | JPEG | 31.44 | 1.23 | 41.22 | 9.13 | 1.97 | 13 |
| 修正後 | AVIF | 14.30 | 1.69 | 33.90 | 4.22 | 3.63 | 20 |
| 修正後 | JPEG | 10.80 | 1.27 | 38.61 | 9.13 | 3.63 | 22 |

生成領域はカタログの `.previews` 以下の論理バイト数を100ms間隔で標本化した。原本、カタログDB、WebViewプロファイルは集計外。メモリは250ms間隔のプロセスワーキングセット合計で、WebViewとGPU専用メモリは含まない。完了キャッシュの再走査はバックエンドのscan呼び出しで測り、再生成は0枚だった。

Nikon ZRの6枚だけで同じ走査を行うと、AVIFの平均は18.69秒から7.98秒になった。各2回、各回とも12画像を保存した。

全46画像を検査して再走査した後、一時作業領域も含めた容量は、修正前33.90MiB、修正後33.90MiBだった。ここには選択写真の先読みも含まれる。

Nikon ZRの異なる3枚を1回ずつ測った。数値は「平均 / 95パーセンタイル」のms。95パーセンタイルはnearest rankで求めたため、3試行では最大値となる。

|---|---|---|---|---|
| 修正前 | 先読み済み | 195.2 / 203.6 | 62.1 / 94.4 | 31.0 / 32.7 |
| 修正前 | 先読みなし | 3368.7 / 3456.9 | 46.6 / 48.0 | 28.8 / 31.5 |
| 修正前 | 別フォルダーを取り込み中 | 5738.0 / 5806.0 | 44.0 / 47.7 | 33.7 / 39.2 |
| 修正後 | 先読み済み | 25.3 / 28.1 | 62.2 / 98.5 | 30.6 / 32.7 |
| 修正後 | 先読みなし | 20.2 / 21.0 | 39.1 / 42.3 | 32.4 / 34.6 |
| 修正後 | 別フォルダーを取り込み中 | 24.2 / 25.8 | 47.9 / 49.0 | 35.8 / 38.0 |

切り替えボタンのクリックから、対象の画像がデコード済みで表示領域にある最初の描画フレームと、露光量が有効になる最初のフレームを別々に観測した。入力反映は実際にマウスでスライダーを操作し、その入力による384px画像がデコードされるまでを測った。「準備後」はヒストグラム表示から4秒待って最初に入力した測定。

先読み済みの写真では、露光量が使えるまでの95パーセンタイルは98.5ms、準備後の初回入力から反映までは32.7msだった。3試行とも暫定値の300ms、100ms以内だった。

同じ試験を、露光量が有効になった直後に入力して繰り返した。

| 入力時の状態 | 修正前（ms） | 修正後（ms） |
|---|---|---|
| 先読み済み | 1461.6 / 1745.9 | 52.4 / 66.3 |
| 先読みなし | 1638.0 / 1670.3 | 1583.5 / 1611.2 |
| 別フォルダーを取り込み中 | 6422.3 / 7023.1 | 1901.8 / 1965.2 |

切り替え直後の入力が画像に反映されるまで、先読み済みでは平均52.4ms。先読みなしでは平均1.58秒、一括生成中に先読みのない写真へ移ったときは平均1.90秒かかった。

先読み済みの条件では選択写真だけを先読みさせ、表示用PNGの生成を待った。先読みなしは待ち行列と準備済みの先読みを空にしてから切り替えた。一括生成中の条件では同じ23枚の複製を入れた別の未走査フォルダーを取り込んだ。切り替え時と入力時の両方で生成が続いており、実際に新規生成したことも検査した。この複製は素材の枚数には加えていない。

## どの処理を変えたか

- その写真の有効な閲覧画像または一覧画像を表示し続け、現像画像のデコードが終わってから置き換える。写真ID、ルート・原本パス、サイズ・更新日時、編集世代と要求番号を照合する。露光量は設定が届けば変更でき、撮影情報を使うホワイトバランスなどは情報の到着を待つ。保存済みの圧縮画像は表示にだけ使う。
- 原本・設定・サイズ・現像バージョンが同じ要求は、先読みの実行中に前面操作が来ても同じ結果を受け取る。PNGの表示は編集用TIFFの読み込みを待たない。選択写真は操作用384pxの既存ワーカーも並行して準備する。保持する先読みは従来どおり最大7枚。
- 色合わせ用384pxと閲覧用1600pxでは、同じRAWのデコード済み入力から別々のrtengineプロセッサーを作る。各サイズの現像方式は維持し、色合わせ用画像をディスクに追加保存しない。Sony SRFは修正前でも並列実行の画素値が変動したため、元のデコード経路を使う。
- 一括取り込みでは専用ワーカーを再利用し、最終画素をパイプで受け取る。単発ワーカーはジョブ専用の一時PNGを使い、完了時に消去する。前面で現像している間は新規の背景処理を待たせる。ジョブごとの一時領域で処理し、共有キャッシュへの公開だけを直列化した。削除とバックアップは処理中のジョブと排他になる。

- Windowsでは論理CPUが16以上、物理メモリが30 GiB以上、カタログを開いた時点の空きメモリが8 GiB以上なら、最初の生成ジョブが終わるまでは2並列、その後は最大4並列とする。それ以外のWindows機とmacOSの既定値は2並列。

## 画質、保存、復旧

- 圧縮前のRGB画素を23枚・37条件で比較した。NEFでは露光量、切り抜き、回転、左右反転、部分マスクも含めた。標準並列で36条件が完全一致した。Sony DSC-F828のSRFは修正前同士でも一致しない。OpenMPのスレッド上限を1にした対照試験では、修正前2回と修正後2回が同じ画素ハッシュになった。提出版でSRFだけを1スレッドとした再試験では37条件すべてが一致した。
- 実際のAVIFをWebViewでデコードしても、SRF以外の22枚は384pxと1600pxの両方で画素ハッシュが一致した。
- 無圧縮の1600px表示を基準に、同じWebViewのRGB値で比較した。元の画素が安定している22枚の総二乗誤差から求めたPSNRはAVIFが34.30dB、JPEGが35.38dB。既定形式はAVIFを維持した。
- Nikon ZRの6枚を1ワーカーで6巡した。各巡の終了時のプライベートメモリは739.03〜742.45MiBで、36件の範囲では増え続けなかった。ワーカーの強制終了とキャンセルの後に、次のRAWを正しく現像できた。
- 一時カタログで編集履歴を保存し、取り込みを中断、再開した。生成中に計測用アプリを強制終了して再起動し、46件の両サイズ、履歴、オフラインでの画像デコードを確認した。カタログで参照されない画像と、所有者を失った作業フォルダーは残らなかった。
- この復旧試験では、完了直後に選択写真の先読み1件が一時領域に残った。ジョブの中間ファイルは消去し、選択写真と近傍の先読みだけを最大7枚分保持する。

- JPEGでの一括生成中の準備後入力は67.1 / 73.3ms（平均 / p95、3試行）。

## 検証

- フロントエンドの型チェック、Viteビルド、単体テスト、EdgeのUIテスト、起動画面・利用規約・フォルダーの個別テストを実行した。写真Aの遅い結果が写真Bを上書きしないこと、右クリック、メニューキー、Shift+F10、入力欄のショートカット、パン、切り抜き、マスク、スライダーを確認した。
- desktopクレートの通常試験は69件成功。実RAWを使う先読み、ライブラリ画素、ワーカーの故障・復旧を別途実行した。Windowsの実機でも、写真・フォルダーのメニューとファイル情報のコピー、切り抜き・マスクの保存を確認した。100%表示で40pxドラッグすると、拡大率を保ったまま表示位置が40px移動した（許容誤差2px）。B→A→Bと連続して選び、最後に表示された画素がBを単独で現像した結果と一致することも確かめた。200回のレンダーと20件の競合要求を含む試験でも、キャンセル後の再開、キャッシュの保持上限、再起動を確認した。develop-coreは75件、rtengineは3件の通常試験が成功した。ネイティブのDCP増感、ディテールの倍率、繰り返し露光の契約試験も成功した。
- 今回実機で確認したOSはWindows 11。macOS実機での操作と性能、NAS、1,000種類のRAWでの900秒判定は未検証。

## 再現手順

Node 24、WindowsのC++/Rust開発環境、WebView2を使う。依存関係は開発手順に従う。[開発環境の手順](../DEVELOPMENT.md)

修正前と修正後のチェックアウトで同じReleaseビルドを作り、異なる空のフォルダーにステージする。測定したPCでは修正前が `.tools/perf-before`、修正後が `.tools/perf-after`。次の例は各チェックアウトのルートで実行する。

```powershell
$localNode = Join-Path $env:USERPROFILE ".local/node-v24.22.2-win-x64"
if (Test-Path "$localNode/node.exe") { $env:PATH = "$localNode;$env:PATH" }
. ./scripts/windows-dev.ps1
npm --prefix desktop ci
npm --prefix desktop run build
$env:CARGO_ENCODED_RUSTFLAGS = "--remap-path-prefix=$env:USERPROFILE=/build/home" + [char]31 + "--remap-path-prefix=" + (Get-Location).Path + "=/source/OpenRoom"
cargo build --release --features custom-protocol --manifest-path desktop/Cargo.toml --locked
cargo build --bin advanced-explorer --locked
$stage = ".tools/perf-after"  # 修正前は .tools/perf-before
New-Item -ItemType Directory -Force -Path $stage | Out-Null
$native = (& $env:OPENROOM_PYTHON scripts/build-rtengine.py) | ConvertFrom-Json
@($native.library) + @($native.runtime) | ForEach-Object { Copy-Item -LiteralPath $_ -Destination $stage }
Copy-Item -LiteralPath $native.data -Destination "$stage/rtengine" -Recurse
Copy-Item -LiteralPath target/release/advanced-explorer-desktop.exe -Destination $stage
```

17枚の公開RAWは `python scripts/fetch-media-fixtures.py .tools/raw-assets` で取得できる。ZRの公開NEF 6枚は測定条件に記載した配布元から取得し、`.tools/raw-zr` に置く。SHA-256は測定データで照合できる。

以下は修正後のチェックアウトで実行する。既存の2つの実行ファイルと同じRAWフォルダーを指定する。ベンチマーク用の環境変数が残っていないPowerShellで実行する。プレビュー未生成の一時カタログを毎回作り、試験用の複製を終了時に消去する。出力はJSON Lines。

```powershell
$cli = "target/debug/advanced-explorer.exe"
$raw = ".tools/raw-assets"
$zr = ".tools/raw-zr"
$before = ".tools/perf-before/advanced-explorer-desktop.exe"
$after = ".tools/perf-after/advanced-explorer-desktop.exe"
$env:AE_BENCH_FORMATS = "avif,jpeg,jpeg,avif"
node scripts/benchmark-raw-import.cjs $before $cli $raw $zr
node scripts/benchmark-raw-import.cjs $after $cli $raw $zr
```

現像を測るときは `AE_BENCH_FORMATS=avif` と `AE_BENCH_UI=1` を設定する。直後の入力はさらに `AE_BENCH_IMMEDIATE=1`。復旧試験は `AE_BENCH_RECOVERY=1` で、強制終了する対象は起動した試験用プロセスツリー。実機のメニュー・パン・切り抜き・マスクは `AE_BENCH_INTERACTIONS=1`。処理別のCSVは `AE_PREVIEW_TIMINGS` にあらかじめ作成した空フォルダーの絶対パスを指定する。

並列数を固定するには `AE_BENCH_IMPORT_WORKERS=2` または `4` を指定する。単発ワーカーの比較は `AE_BENCH_SEPARATE_WORKERS=1`、RAW再読込の比較はさらに `AE_BENCH_FRESH_RAW=1`。単発処理の既定はPNG。比較用の非圧縮RGBは `AE_BENCH_RGB_HANDOFF=1` を加える。比較後は環境変数を解除する。PSNRの比較では `AE_BENCH_REFERENCE_EXE` に修正前の実行ファイルを指定し、`AE_BENCH_FORMATS=avif,jpeg` を使う。

```powershell
python scripts/compare-raw-previews.py $before $after $raw $zr --serial-srf
python scripts/benchmark-import-worker.py $after $zr --passes 6
npm --prefix desktop run test:ui
node scripts/test-desktop-ui.cjs --terms
node scripts/test-desktop-ui.cjs --catalog-folders
cargo test --manifest-path desktop/Cargo.toml --locked
cargo test --manifest-path crates/develop-core/Cargo.toml --features rtengine
cargo test --manifest-path crates/rtengine/Cargo.toml
```
